# Goober viability and compatibility failures

Research date: 2026-10-23. Scope: research only, [issue #5](https://github.com/ankit-thesys/openui-comp/issues/5). Prototype evidence baseline: [`09a336f3`](https://github.com/ankit-thesys/openui-comp/commit/09a336f3). No adoption decision or component migration is made here.

## Recommendation

**Goober remains conditionally viable if OpenUI owns a bounded build-time CSS integration.** The observed failures do not establish a general Goober incompatibility with Tailwind, Bootstrap, React 19, or Next.js. They primarily expose cascade policy and stylesheet delivery mistakes in our prototype. Additional integration code can address those tested cases; it does not make arbitrary runtime CSS generation or every consumer layout automatically safe.

Prefer Goober as a package-build style generator, publishing ordinary static CSS and stable classes. Keep variable themes and chart updates within a finite style vocabulary, using CSS variables/data attributes where allowed by the host's CSP. This recommendation follows the existing successful prototype, not an upstream turnkey extraction product: [`generate-styles.mjs`](../scripts/generate-styles.mjs), [`configure.mjs`](../package-prototype/configure.mjs), and [`auto-button.js`](../lib/auto-button.js).

## What failed, and whose responsibility it is

| Observation | Evidence and attribution | Consequence |
| --- | --- | --- |
| Default policy lost some consumer overrides; layered policy lost some base styles | The baseline [decision report](../results/DECISION.md) records default 5/10 complete scenarios, layered 8/10, adapted 10/10. Changing scoping/layer policy changes the outcome with the same engine. CSS layers rank normal unlayered rules above layered rules; later source order alone cannot defeat a higher cascade rank. [CSS Cascade specification](https://www.w3.org/TR/css-cascade-5/#layer-order) | Integration must select a coherent cascade policy. This is not evidence of a Goober parser defect. |
| Host `_goober` contents/position were disturbed in the earlier adapter | The corrective [isolation commit](https://github.com/ankit-thesys/openui-comp/commit/c9c7cd7a) and current [`lib/goober.js`](../lib/goober.js) switch the adapted path to a library-owned tag and explicitly forbid moving or clearing the app sheet. | Prototype ownership bug. A library must not rearrange the host's shared Goober sheet. |
| React resource CSS overrode unlayered Tailwind v3/plain/Bootstrap app styles in Next | The [early-import change](https://github.com/ankit-thesys/openui-comp/commit/09a336f3) replaces late inline resource delivery in the installed-package path with a generated stylesheet imported first in the root layout. [Recorded compatibility results](../results/COMPATIBILITY.md) then pass all 10 executed combinations. | Framework delivery/cascade integration. React's `precedence` ranks resource styles by discovery; it is not a promise to place defaults before all host CSS. [React style reference](https://react.dev/reference/react-dom/components/style) |
| A component `nonce` prop did not authorize the React resource style | [CSP results](../results/CSP.md): prop-only probe fails; renderer style nonce, hash, and external stylesheet probes pass in both executed engines. React documents that resource-style handling drops extra props. [React style reference](https://react.dev/reference/react-dom/components/style) | React delivery/CSP contract, separate from Goober's runtime tag creation. Next-integrated streaming nonce behavior still requires testing. |
| Goober formerly appended its runtime tag before setting its nonce | Actual upstream bug: [PR #613](https://github.com/cristianbote/goober/pull/613), fixed in [v2.1.18](https://github.com/cristianbote/goober/releases/tag/v2.1.18). [v2.1.19 source](https://github.com/cristianbote/goober/blob/v2.1.19/src/core/get-sheet.js) sets `el.nonce` before append. | Use the fixed version for runtime evaluation. This historical bug does not explain our React resource prop-only probe. |

## Upstream maintenance: alive, with limits

As checked on the research date, [GitHub repository metadata](https://api.github.com/repos/cristianbote/goober) reports `archived: false`; its last push is 2026-05-13. The [latest release](https://github.com/cristianbote/goober/releases/tag/v2.1.19), published 2026-05-13, includes migration from WMR to Vite and size changes. The preceding CSP correction shows a concrete contributor fix accepted and released in October 2025. These establish continued maintenance activity, not response-time guarantees or broad React/Next certification. There has been roughly five months without a push; plan to own integration fixes and pin/test upgrades rather than relying on rapid upstream intervention.

Goober's [documented API](https://github.com/cristianbote/goober/blob/v2.1.19/README.md#targets) supplies custom targets and CSS extraction. It does not supply OpenUI's framework detection, source metadata, reports, theme/portal policy, or installer. Its small core makes an adapter plausible, but small bundle size is not a maintenance-cost measurement.

## Runtime SSR has a different cost

In [v2.1.19 `get-sheet.js`](https://github.com/cristianbote/goober/blob/v2.1.19/src/core/get-sheet.js), the no-DOM fallback is a module-global `ssr` object unless a target is supplied. [`extractCss`](https://github.com/cristianbote/goober/blob/v2.1.19/src/core/update.js) reads and empties that sheet. **Inference from source:** interleaved requests sharing the default sheet can mix or drain each other's CSS. A global clear before/after render is insufficient isolation for streaming concurrency. A runtime adapter would need request-owned targets throughout every generation path, correct flush timing, cancellation/retry behavior, and hydration tests.

[Next's CSS-in-JS guide](https://nextjs.org/docs/app/guides/css-in-js) warns that concurrency/streaming require library support and describes per-render collection and insertion before dependent content. Goober is absent from its supported list; absence alone proves neither incompatibility nor certification. [Next's CSS guide](https://nextjs.org/docs/app/getting-started/css#ordering-and-merging) makes import order relevant and explicitly requires checking production builds because ordering can differ from development. Build-time CSS avoids request-time Goober collection; OpenUI still owns import/cascade integration.

## Boundaries before adoption

- Current evidence is a representative Button, five production Next apps, Chromium and Playwright WebKit: **10/10 executed combinations pass**. Firefox's five planned combinations are unavailable due to launch/profile failure, not failed styling assertions. WebKit is not Safari release certification. Use [compatibility.json](../results/compatibility.json), [CSP.md](../results/CSP.md), and [COMPATIBILITY.md](../results/COMPATIBILITY.md) over stale broad limitations in the aggregate decision report.
- The installer supports conventional App Router layouts and directly installed Tailwind v3/v4 or Bootstrap; it refuses ambiguous roots or changed generated files. CDN CSS, unusual monorepos, custom layers, import resorting, and other frameworks remain integration work. Users run a setup command; this is automated setup, not setup-free integration.
- Static extraction enumerates known rules/variants. It does not automatically capture arbitrary prop-generated runtime rules. Initial CSS includes delayed variants, which trades delivery simplicity for payload size. Current external components still import the artifacts object containing CSS strings: external delivery alone does not establish that duplicate CSS text is absent from client JavaScript. Packaging/performance must be measured separately.
- Before adoption, port actual components, validate supported browsers/React/Next versions and production navigation/streaming, test strict CSP including dynamic values, and measure CSS/JS payload and rendering cost. Preserve host-sheet isolation, source metadata and generated compatibility checks as maintained OpenUI tooling.

**Answer:** yes, a maintained integration is plausible and the strongest demonstrated path is static generation. The earlier failures mostly came from our policy and delivery choices. There is one verified historical upstream CSP bug, already fixed, and a source-evidenced runtime SSR isolation hazard requiring deliberate engineering. Neither a universal compatibility claim nor a production adoption decision follows from these results.
